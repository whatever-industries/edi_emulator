# CD-i display geometry and presentation

## Model boundary

`cdi-core` reports the digital signal generated by the MCD212. Its public
`DisplayGeometry` is derived only from the player standard and live `CF`,
`ST`, `FD`, `SM`, and field-parity state. MCD212 Compatibility Mode is part of
that hardware geometry.

The frontend always presents that hardware-defined active picture. It does not
simulate analog television overscan, inspect framebuffer contents to choose a
crop, or expose a host-defined CRT/full-signal mode. Rendering, screenshots,
window aspect, and pointer endpoints consume the same core aperture. Authored
padding therefore remains visible unless the guest selects an MCD212 hardware
Compatibility Mode.

Normal presentation uses the measured Philips player pixel aspect. The
optional raw-square-pixel diagnostic changes only pixel shape; it never crops
or repositions the core aperture. Real television overscan varied by set and is
outside the emulated player boundary.

Green Book V.4.8 distinguishes 525-line **monitor** and **TV** outputs.
Compatibility mode is a centered 360-pixel picture on the 525 TV output but a
384-pixel picture on the 525 monitor output; the mode-zero meanings are
reversed. The current CD-i 220 model represents the TV output. A future
monitor-class player must be an explicit player-model distinction rather than
an inferred per-title crop.

## Philips evidence

The local ICDIA technical-note mirror is the primary source. OCR sidecars are
generated into ignored `tmp/pdfs/cdi-technical-notes-ocr/`; neither those
derived files nor the original documents are redistributed by this project.

- TN 042, *Reduction of Flicker in Interlaced Pictures* (1989), explicitly
  describes a whole-screen picture as overscanning.
- TN 048, *Preparing CD-I Titles for the International Marketplace* (1989),
  describes adding 20 neutral lines above and below 240-line NTSC material on
  a PAL player, and distinguishes that compatibility treatment from native
  384x280 PAL authoring.
- TN 063, *Display Synchronization in CD-I* (1991), gives a synchronized
  display-program structure whose top line may be black because it is
  typically hidden by television overscan.
- TN 069, *The Technical Status of the Philips 910 CD-I Player* (1991),
  records a real player's roughly 12-pixel horizontal timing displacement and
  warns against software-shifting the entire image to compensate for one
  hardware revision.
- TSA-003 / TN 093, *Image formats for Compatibility* (1992), defines pixel
  aspect as pixel height divided by width. It gives theoretical CD-i ratios of
  1.19 (525) and 1.05 (625), then measured Philips-player values of 1.225 for
  525-line output (384 samples in 50.84 us) and 1.025 for 625-line output
  (384 samples in 51.2 us). E-Di stores these exactly as 49/40 and 41/40.
  The note's 320x210 safety area is authoring guidance, not a mandatory
  emulator crop.

TN 093 also says the same bitmap will appear vertically stretched on a
525-line player and compacted on a 625-line player, and reports that regional
assets may be authored separately. Consequently, a PAL/NTSC screenshot
difference is not sufficient to change geometry: compare the exact disc,
source dimensions, live MCD212/MCD251 state, and presentation boundary first.
The ongoing source ledger and test queue are in
`docs/specification-research.md`.

## The Apprentice diagnosis

The Apprentice USA runs on the NTSC/60 Hz player setting. At its title and
gameplay screens the live MCD212 state is full TV mode (`CF=1`, `ST=0`,
noninterlaced), so the correct digital signal remains 384x240. The title's
display-control program independently creates a 360x220 picture at normal
resolution: its visible bounding box is x=12..371 and y=20..239, or
x=24..743/y=40..479 in E-Di's double-resolution framebuffer. That authored
picture is bottom-aligned within the signal. E-Di preserves the complete
hardware aperture, including that placement and any surrounding padding.

The title developer's surviving technical note also documents that the main
game deliberately uses black top/bottom borders as sprite-overflow space.
Those internal gameplay borders are title graphics and are not removed by
host presentation.

With the measured NTSC pixel aspect, that intended viewing area is:

```text
360 / (220 * 1.225) = 1.336
```

which is effectively 4:3. The complete 384x240 signal is only 1.306:1 after
the same correction. This explains why a historically simulated television-
safe crop appeared close to 4:3, but it is not a specified player aperture.
Different intro screens may contain their own padding inside the signal; the
hardware aperture preserves those differences instead of resizing every
scene.

An older MESS/MAME result is not a reliable geometry oracle here. Historical
MCD212 code failed to stop implicit region-control register scanning after an
operation-0 instruction, contrary to the MCD212 specification. Reproducing
that behavior can make some frames look fuller but changes the emulated
display program. E-Di retains the specified operation-0 termination.
